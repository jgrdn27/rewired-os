# Work review

These are project workflows. Resolve paths from the OS workspace root containing `AGENTS.md` and `START-HERE.md`; do not install this skill alone.

Read the selected period's work records, previous review if relevant, and current goals. Prepare a short evidence-based review before asking questions. Separate actual delivery from reported completion, proposals, and unknown outcomes. If little evidence exists, ask one focused question rather than inventing a week of activity.

Identify the most consequential observed friction: repeated correction, missing input, failed handoff, excessive steps, or slow retrieval. Explain the benefit of addressing it and propose one bounded next change, including a way to test usefulness. Doing nothing is valid when there is no supported opportunity. Do not require an automation or a new skill.

If the user selects implementation, reuse the existing workflow where possible, define the output and acceptance check, and build within that authorization. Prefer deterministic handling for clear rules and human review where judgment matters. Scheduling, publication, and external communication need their own scope.

For a requested saved or recurring review, create a unique dated record under `reviews/` with evidence, proposed change, user decision if any, and next check. Never rewrite historical reviews or count repeated synthetic tests as real adoption. For conversational advice, keep the answer in chat.

End with one useful next action or a clear no-change conclusion. During later reviews compare actual time, revision burden, or failed runs only when there is comparable evidence.
