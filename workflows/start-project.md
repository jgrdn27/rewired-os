# Establish continuity

Read `work/index.md` and `docs/projects.md` from the Rewired root. Check whether the outcome already has a project folder or an authoritative record in another tool. Preserve that authority and organization.

Extract the desired outcome, completion criteria, available evidence, and first useful action from the request. Keep unknown owners, dates, and resources explicit. Ask only for missing information that changes the work. A small task can stay in one deliverable without a project scaffold.

For a new local project, use `templates/project.md` at `work/<descriptive-slug>/PROJECT.md`. Check for an existing destination, including case differences. Reuse it when appropriate; never overwrite unrelated content. Adapt the fields to the project rather than creating empty stages.

For existing or external projects, add only the missing continuity information. Link evidence and deliverables instead of duplicating their contents. Identify the status authority and last observation date. Use a local brief only when it adds value within the request.

Add a concise route from `work/index.md`. If writing is unavailable, return an unsaved brief or an authorized contributor handoff. Do not report setup as persisted until the destination has been checked.

When the request includes execution, continue beyond setup to the next authorized action. Check the result against the project's completion criteria and the fresh-reader questions in `docs/projects.md`. Leave exact artifact links, unresolved conditions, and the next action. Do not claim a separate-session test unless one ran.

Tools, library activation, stage gates, deadlines, and external actions are not mandatory consequences of starting a project.

When the request involves executing a repeatable process, read `docs/playbooks.md` and use `workflows/run-playbook.md`. The project brief links to its runs; each run keeps its own checkpoint evidence. Do not add run records to a one-off task without a useful reason.
