# Repeat the method, keep each result

A playbook describes a process worth repeating. A run records what happened on one occasion. Use these when the work has meaningful checkpoints, such as producing an issue of a newsletter, preparing an event, or delivering a sponsor campaign. Keep simple tasks in their existing artifact.

## Fit into the project

Start through [Run a playbook](../workflows/run-playbook.md). Reuse the project brief and its authority from [Projects](projects.md). For a local project, a typical layout is a user-owned `work/<project>/playbook.md` and `work/<project>/runs/<occasion>/RUN.md`, with that occasion's deliverables beside the run. Existing folders work equally well. Never rearrange them to match this example.

Use the [playbook template](../templates/playbook.md) for a requested new method and the [run template](../templates/playbook-run.md) for its execution. These are writing aids, not required parsable formats. No runtime, account connection, background service, or GTM activation is needed. Dates do not create reminders.

`work/index.md` links to the project. Its brief links to each run. The run owns local checkpoint progress; the brief need not repeat it. If an external system already owns progress, the run links to its records and labels local observations with their dates. Do not create a competing status system.

## Give each checkpoint a test

To capture a process after useful work, ask to [save a playbook](../workflows/save-playbook.md). The method should keep what is repeatable and link to its supporting work. A successful draft does not validate later publication or measurement steps. Shared user methods can live in `work/methods/`, linked from the work index; they remain personal files through updates.

For each useful checkpoint, capture the intended result, what must be available first, and what evidence establishes completion. Record the selected criteria in the run. A link to a changing playbook alone is insufficient: a later method edit must not rewrite what an earlier run agreed to deliver. Change a live run's criteria only within the user's request and record why.

Use these plain-language states when helpful:

| State | Meaning |
|---|---|
| Open | Work remains and has not started. |
| Working | Work has begun; the completion check has not passed. |
| Waiting | A named input, decision, time, or capability is missing. |
| Complete | The stated completion check passed with linked evidence. |
| Skipped | Intentionally omitted with a recorded reason; not a completed result. |
| Recheck | Earlier evidence is missing, changed, or contradicted. |

A draft can complete a drafting checkpoint while review and publication remain unfinished. Skipping a required result leaves the overall outcome unmet unless the user changes that outcome. Archive or abandon a run with its reason; preserve prior work.

For waiting work, name the condition and how to verify it. Record a known date and timezone only when relevant and supported. On resumption, check the condition; the passage of time does not establish a customer's response, approval, or successful execution.

## Tie decisions to the actual artifact

Keep approval evidence and action scope together: who authorized what, when, and which artifact or version it covers. Approval of a draft's content and authorization to publish are separate facts. Use existing authorization without asking again. If a material edit changes approved content, retain the approved version and identify the changed version as needing the applicable review.

Prefer separate filenames for material deliverable versions. If content is updated in place, record enough revision evidence to identify what was reviewed and recheck dependent checkpoints. Do not describe a file as approved merely because an older version was approved.

Save each useful result before advancing the record. If interrupted between the two writes, inspect the actual artifact and reconcile the record on return. For external operations, preserve any returned reference and distinguish attempted, accepted, and verified outcomes. An uncertain publishing result calls for a status lookup, not a blind repeat.

## Leave enough to continue

The run should answer: what is being delivered, which criteria apply, what has evidence, what remains, and what the next assistant is authorized to do. Link the newest useful artifact and the sources behind it. Preserve significant changes instead of overwriting the history with a reassuring summary.

Use one writer at a time. Apply the [access and synchronization rules](portability.md) when changing device or provider. If the canonical record cannot safely be updated, leave an explicitly unsaved continuation or a separate authorized handoff. Never claim that a local edit has reached another device without checking.

The [fictional sponsor playbook](../examples/sponsor-playbook.md) illustrates the method. It is not active work. The [resumption pilot](playbook-testing.md) checks whether assistants can actually use saved records.
