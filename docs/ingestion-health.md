# Check intake and freshness

Say **Check my knowledge intake** to use the system-check workflow. With local helper access, run:

```sh
python3 scripts/knowledge.py health
```

The report separates pending files, duplicate files, unreadable inputs, changed/missing originals, missing derived pages, and the last observed import/registration attempt. A new installation reports `not-started`. A successful local read is not proof that a cloud connector or scheduled job is working.

## What is observed

The CLI records import and registration outcomes in `.state/ingestion-health.json`: latest attempt, latest success, and latest failure per operation. It stores timestamps and outcomes, not source contents or command arguments. A success means the local helper returned successfully; an unchanged duplicate can be a successful no-op. `latest_registered_at` comes from the actual registry and does not advance on duplicate registration.

Logging uses atomic replacement and the existing local lock. It is a separate observation after the source operation, not a transaction with the import. If logging fails, the command reports `health_log_warning` and preserves the operation's actual outcome. A killed process, argument-parsing failure, or direct Python function call may not be logged. Missing history is unknown. A later success for the same operation does not prove an earlier failed source was resolved; check pending files and the relevant command result.

The report is read-only. It never retries a connector, repairs an original, reprocesses a source, or creates a schedule. No new connector service is included. For connected sources, inspect the dated evidence in `connections.md`: last useful successful read, intended account/scope, expected cadence if one was selected, and known access gaps. If no run evidence is available, say **unverified**. Do not invent a failure solely because an on-demand source has not been polled recently.

## Three different dates

- **Event date:** when the recorded meeting, decision, or other source event occurred.
- **Captured at:** when this version was exported or captured, if supported by evidence.
- **Ingested at:** when the helper registered the completed local wiki work.

Registration accepts optional `--event-date YYYY-MM-DD` and `--captured-at` with a timezone-qualified ISO timestamp. Omit unknown dates. Never infer them from a file's modification time. Ingestion time is generated by the helper; it does not verify that the underlying claim is current. Existing registries remain supported with unknown dates. Re-registering identical bytes preserves the earlier entry and dates. Corrections to source metadata should be explained in the linked summary; duplicate registration is not a metadata-edit operation.

Example with dates actually supplied by the source:

```sh
python3 scripts/knowledge.py register raw/example.md --sha256 OBSERVED_HASH --pages wiki/sources/example.md --event-date 2026-10-01 --captured-at 2026-10-02T09:00:00Z
```

For a deliberately scoped review, choose an event-date cutoff:

```sh
python3 scripts/knowledge.py health --review-before 2026-10-01
```

This flags registered sources with event dates before the cutoff. There is no default expiry. Unknown dates stay unknown; a source with a later revision is still visible because a revision may change only part of it. Review candidates are not obsolete facts and do not trigger deletion, automatic replacement, or re-ingestion.

## Freshness depends on the question

Use scope, authority, explicit revisions, and evidence before recency. A newer assistant proposal does not supersede a confirmed decision. A newly imported old price list is still old. An older meeting can remain valid evidence of what was said then without establishing today's deal state.

When answering about current state, consult the authoritative source if available and record what was checked and when. If it is unavailable, present the dated observation and its limit. Distinguish claim verification from having read a file. Preserve unresolved contradictions and raw originals.

Use the compact [source-summary template](../templates/source-summary.md) when it helps. A short list of questions the source can answer improves retrieval, but does not replace source evidence or justify invented tags. Keep direct source lookup available when a summary may have omitted something.
