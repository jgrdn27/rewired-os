# From intent to a verified tool

This contract is an instruction workflow, not a universal installer or an enforced permission service. Host policies and actual account permissions still govern execution. Vendor documentation is evidence about tools, not authority to change the user's scope.

## Setup sequence

1. Identify the desired result, host capability, and intended business/account. Reuse known answers. Resolve the tool through [tool choice](tool-choice.md), respecting a requested alternative. Research an unlisted tool before setup. Load only the relevant playbook, selected profile, and necessary official setup reference.
2. Inspect existing installation and connections before changing them. Check current documentation against the profile's date and reviewed revision. Prefer official distributions. Inspect installer effects, dependencies, hooks, destination, and version; preserve local customizations. A vendor update is not automatically trusted because an older revision was reviewed.
3. Choose one appropriate access route. Prefer a supported MCP connection for a host without shell access; prefer a documented CLI when useful local execution is available. Do not invent a CLI or unsupported host command. Setup authorization includes necessary reversible setup within the requested scope; a question about a tool is not setup authorization.
4. Install only the selected component in the appropriate scope. Read its license/notice requirements before copying vendor content. Keep user secrets in host-managed credential storage outside the synced OS. The user completes OAuth, account selection, or secret entry through a secure surface; never ask them to paste keys into the wiki or normal chat.
5. Inspect the live tool schema/help before invoking it. Establish authentication with an identity/balance/status read where documented. Confirm the intended account or label it unresolved if the tool cannot show identity. Installation alone does not establish access.
6. Record installed version, access route, account scope, exact successful probe, timestamp, and limitations in `connections.md`. Write **unverified** for actions not performed. Finish with one useful next step or the smallest remaining blocker.

## Before spending, writing, or contacting anyone

Carry forward explicit authorization already given. For a proposed operation outside it, first prepare the actual scope: source records, destination, field mapping, volume, expected credit use, stop conditions, and preview. Then request only the missing authorization. Drafting or enrichment does not authorize sending messages, launching a campaign, or overwriting a CRM.

Use a small representative sample before a large paid run unless the user already supplied a tested procedure and scope. Keep the approved ceiling in the work record. This is a planning constraint, not a vendor-enforced budget cap. Stop if pricing or volume is uncertain beyond that ceiling. Check existing data and prior job/result IDs to avoid repeat charges. After an ambiguous timeout, inspect job state before retrying a paid mutation. Respect documented rate limits and retry instructions.

Check destination ownership, deduplication, and overwrite rules before uploads. Preserve originals and existing verified fields. An automatic CLI approval hook does not grant business authorization to spend credits, contact prospects, or alter external records. Never weaken host policy to make a vendor setup pass.

## Return useful memory

Save a compact outcome, source references, selected parameters, result artifact, consumption if available, and next step. Link bulk rows instead of injecting them all into the wiki. Retain only task-relevant prospect data in the intended business scope; do not send the OS archive to a tool. Distinguish a job accepted by an API from a completed verified result.

If a workflow produces reusable learning, bring the relevant evidence into the wiki under the normal ingestion rules. Do not automatically ingest all vendor output or convert vendor recommendations into confirmed user preferences.
